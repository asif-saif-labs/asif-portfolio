At work, alerts from our monitoring land as tickets in a NOC queue. One
afternoon I picked up a backlog of about 20 of them, most of them some flavour
of "5xx errors on the load balancer". I traced every one read-only, with no
changes, and wrote up the cause on each ticket.

The pattern was clear by the end: very few of these were outages. Most were
the load balancer telling the truth about services nobody was looking after.

## 503, 502 and 504 on an ALB are different problems

The first thing to read is which code it is and whether the ALB or the target
produced it. CloudWatch keeps them apart: `HTTPCode_ELB_5XX_Count` is
generated by the load balancer itself, `HTTPCode_Target_5XX_Count` came from
your app.

| Code | Generated by the ALB when... | Look at |
|---|---|---|
| 503 | the target group has no healthy targets, or no registered targets at all | target health, ECS service, ASG |
| 502 | the target closed the connection, sent a malformed response, or the connection failed | app crashes, keep-alive timeouts, TLS to target |
| 504 | the target didn't respond before the idle timeout | slow app, database, idle timeout setting |

A 503 from the ALB means the request never reached your code. That makes it
the easiest one to triage: the answer is in the target group.

## Check target health first

For each ALB in the alert, list the listener rules and their target groups,
then check health for each group:

```bash
aws elbv2 describe-target-health \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-app/abc123 \
  --query 'TargetHealthDescriptions[].[Target.Id,TargetHealth.State,TargetHealth.Reason]' \
  --output table
```

Two results matter:

- **Empty output.** No targets registered. Every request routed to this group
  gets a 503.
- **Targets present, all `unhealthy`.** The `Reason` field tells you why:
  `Target.FailedHealthChecks`, `Target.ResponseCodeMismatch`,
  `Target.Timeout`. Then go to the service behind it.

To find which rules point at which groups on a busy listener:

```bash
aws elbv2 describe-rules \
  --listener-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:listener/app/my-alb/abc/def \
  --query 'Rules[].[Priority,Conditions[0].Values[0],Actions[0].TargetGroupArn]' \
  --output table
```

## What was actually behind the alerts

### Listener rules pointing at empty target groups

This was the biggest group. Services had been retired at some point, but the
listener rules and target groups were left behind. With no registered targets,
anything matching those rules got a 503. Add internet scanners sweeping the
ALBs for common paths and hostnames, and you get a steady 5xx alarm for a
service that no longer exists.

The fix isn't to tune the alarm. It's to remove the rule and the target group,
or route the host to a fixed response. I raised a decommission request for
these, listing each rule and target group, and asked the owners to confirm
before anything is deleted.

### Target groups with no healthy targets

A smaller set had targets registered but none healthy. These are real
outages, and the target health `Reason` plus the ECS service events showed
where to look. One of these turned out to be a crash-looping deployment,
which I wrote up separately.

### Databases pinned at maximum capacity

Some alerts were about the database, not the load balancer. An Aurora
Serverless database sat at its maximum capacity every week while a scheduled
job ran. Raising the alarm threshold would hide it; the real question is
whether the job should run differently or the max capacity is wrong.

### Under-scaled services

One service ran a single task at 100% CPU with no CPU-based scaling policy,
and its desired count was below the minimum set for it. That is a capacity
setting to fix, not an incident to chase.

### Dead services that still alerted

Several services were simply not in use anymore but still had alarms, health
checks and listener rules. Each one generated tickets someone had to read. I
listed them in the same decommission request.

## Gaps the triage exposed

Two things made it slower than it should have been:

- **ALB access logs were off** on the affected production ALBs. Without them
  you can't see which paths, hosts or clients produced the 5xx. Turn them on;
  S3 storage for access logs is cheap next to the time it saves.
- **Performance Insights retention was 7 days** on the databases. A database
  spike in an older ticket can't be checked anymore. Triage database alerts
  within the week, or raise the retention where it matters.

## Triage checklist

For each 5xx alert:

1. Is it `HTTPCode_ELB_5XX` or `HTTPCode_Target_5XX`? ELB means the request
   never reached the app.
2. Which code? 503 means target health, 502 means the connection to the
   target, 504 means time.
3. Run `describe-target-health` on every target group behind the matching
   rule. Empty means nothing registered; unhealthy means read `Reason`.
4. If targets are unhealthy, check the ECS service events or ASG activity for
   crash loops and failed deployments.
5. Check the database behind the service: capacity, CPU, connections.
6. Check whether the traffic is real users or scanners, using access logs if
   they're on.
7. Ask whether the service is still in use. If not, raise it for
   decommissioning instead of fixing the alarm.
8. Write the cause on the ticket even if no action is needed, so the next
   person doesn't repeat the work.

## Takeaways

A noisy alert queue is usually a cleanup backlog in disguise. Most of my 20
tickets traced back to infrastructure that outlived the service it was built
for. Doing the triage read-only kept it safe and quick, and the useful output
wasn't the ticket comments. It was the list of things to decommission, and
the settings (access logs, scaling policies, circuit breakers) to turn on so
the next batch is smaller.
